# Base — founder testing sheet

Scope: every shipped Base surface through merged #647, with earlier list/product/
contact/campaign/audit work and current main behavior. Baseline `d5d3ea2e`;
branch `codex/base-sheet`. **55 rows**, each proved by one `test_bNN_*` fixture
case in `tests/acceptance/test_base.py`; a separate check enforces the exact mapping.
Merged/code inventory and fixes: [ACCEPTANCE-INVENTORY](../base/ACCEPTANCE-INVENTORY.md).

## Addresses, inputs and evidence

- `/chats` means **https://app.tervory.com/chats**, Base squad, signed in to the
  founder's active US organization. Ask `Run <tool> with <JSON>` and Confirm each
  proposed card, including reads. Copy returned IDs; `<LIST>`, `<UPLOAD>`,
  `<CAMPAIGN>` and `<AUDIT>` stand for actual returned IDs, never literal strings.
- Use founder-owned test records and CRM, existing approved skills and existing
  organization bindings. No fixture/example records are inserted into live screens.
  Live counts, money, dates and model text come from real evidence; fixed numbers
  explicitly marked offline describe fixture assertions, not live promises.
- Internal `http://tank:8000/...` addresses are for the existing authorized founder
  operator session; deployment supplies the existing key privately. They are not
  public browser pages. Do not paste credentials into chat or this sheet.
- Settings are exact names from [FOUNDER-SETTINGS](../ops/FOUNDER-SETTINGS.md).
  `none` means no additional founder-filled setting. Base vault actions require
  existing `base.vault` on except B41; this is an existing Tank switch, not a new
  environment variable. External-service settings are entered only by the founder.
- To review an audit, run `base.audit.csv` with campaign_id/audit_id; Confirm and
  open Result. Check each sampled page/date. Fill verdict with correct/wrong/unsure;
  optional website_verdict, phone_verdict, email_verdict, socials_verdict apply only
  to fields actually checked. Preserve every original evidence cell and record ID.
  Upload to the same chat, then `base.audit.review` with its owned attachment_id.
- `<START>` / `<END>` are ISO dates enclosing the founder evidence; offline report
  fixtures use 2026-10-01 through 2026-10-03.
- A positive audit needs **200 verified records in one campaign**. A smaller DC
  campaign still completes and exports, with unknown audit measurements. Never
  create fake records or claim a fixed accuracy to satisfy that prerequisite.

## Offline proof

The fixture cases follow `test_tisan.py`: reuse actual application paths and their
existing fake external-service harnesses. The DC cases run confirmed command
adapters, real database/store/collector, recorded worker output, audit review and
CSV. Browser plugin cases execute real Base TSX/server actions with only external
boundaries stubbed. Candidate evals do not change approval state. No live provider,
paid feed, real model call or production write is needed for these tests.

Run Python 3.12 with existing test requirements and Workspace/template lockfile
Node dependencies, plus the existing Chromium test runtime. Set TMPDIR to this
checkout's `.tmp`; set BASE_TEST_DATABASE_URL and POOL_SCHEMA_DATABASE_URL only
to isolated loopback PostgreSQL test databases. Without these, DB cases skip and
must not be called proof. Run `python -m pytest -q tests/acceptance/test_base.py`
and the existing `tests/test_base*.py` regression suite. Before every push run
`scripts/precheck.sh`, without gitleaks/Semgrep exceptions. All test containers use
`--rm --label tervory.test=1 --name codex-base-sheet-<purpose>`.

CI and final verification results are recorded in the inventory; offline success
does not assert live deployment or founder acceptance.
