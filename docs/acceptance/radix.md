# Radix — founder testing sheet

Scope: shipped Radix on main at `d5d3ea2eeb08c9b7a9061274504f0acf53bab2a6`, including merged #634 and #651, client consent, bounded infrastructure checks and weekly monitoring. There are **58 acceptance rows**. `tests/acceptance/test_radix.py::test_rNN_*` is the matching offline case; the parity check requires exactly one case for every row.

## Addresses, inputs and settings

- Browser: **https://app.tervory.com/chats**. Radix uses its existing cards, not a new page. Use the founder's active workspace; client checks use a separate Radix-enabled tenant and that tenant's admin. Never paste keys into chat, a URL, a screenshot or this sheet. Existing sign-in, room keys, tenant/region binding and skill approval are prerequisites, not additional settings.
- `http://agent-radix:8000/...` and `http://tank:8000/...` below are **internal operator addresses**, not public browser pages. Use the existing authorized operator session; deployment supplies its key and tenant headers privately. Supplied-business-evidence checks call approved code skills against saved evidence; they do not look up people or fetch arbitrary sites.
- `<DOMAIN>` is a domain whose DNS the tester owns; founder active/infra checks use **tervory.com**, the unchanged own-domain list. `<URL>` means exactly `https://<DOMAIN>/`, without credentials, an explicit port, path, query or fragment. `<SHA>` is a real full 40-character commit, `<SCAN>` the returned tenant-owned scan UUID, `<UPLOAD>` the returned uploaded-attachment UUID, `<EVENT>` the actual Zenas event UUID and `<FINDING>` the gate's actual finding UUID. Never substitute a fixture UUID or fake SHA in live work.
- **B** is supplied tenant-owned business evidence in the shipped schema: tenant/region, business lookup, business/account records and source catalogue with retrieval time and evidence hash. Use the founder's actual evidence for live checks. The offline source is `tests/fixtures/rx5/businesses.json`; its companies, officers, addresses and domains are synthetic. Use a second tenant's own fixture for isolation checks; do not inspect a client's data.
- In `/chats`, request the named tool with the given arguments and click **Confirm**. A proposal alone must queue nothing. Explicit commands such as `radix.watch <DOMAIN> daily` and `radix.report <SCAN>` use the code planner. Other rows name their existing tool arguments; do not invent a command/route or approve a new skill to make a test pass.
- Client active/infra/weekly consent is **the founder's text in FOUNDER-SETTINGS section D1**. `<D1 TEXT>` means that exact supplied written text, not text generated by Radix or this sheet. Record it with `radix.active.consent <DOMAIN> <D1 TEXT>`. The admin who grants it, domain, time and withdrawal remain auditable. A missing approved text/frame is listed for the founder; it is never fabricated.
- Setting names below are copied from **docs/ops/FOUNDER-SETTINGS.md**. “none” means no additional founder setting. `TANK_GITHUB_READ_TOKEN` is the existing fixed-repository read credential on Tank; `RADIX_DEPLOY_TENANT_ID` is a **GitHub repository variable**, not Coolify; gate `TANK_API_KEY` is an existing **GitHub repository secret**, not a new token. Only the founder supplies values privately. No setting is changed by this sheet.
- Use the approved isolated fixtures for malicious archives, synthetic secret findings, malware, critical deploy holds, outages and removed proof. Do not plant keys, malware or deliberately vulnerable code on production, edit a client's DNS, or trigger a real deployment merely to test a negative case. The acceptance cases run the shipped handlers with fake external services and disposable local stores. No live scan, deployment or client approval is claimed by offline tests.

## Scope and missing frames

All rows describe existing finished paths and their evidence; none tests that an open-PR route is absent. There is no newly built page, label, explanatory sentence, consent copy or email. Existing measured-hash/cookie-provenance/partial-coverage explanations still await approved frames; tools' own descriptions and existing card labels remain authoritative. Consent rows require the founder's section D1 wording; this sheet does not invent it. **Missing founder copy/frame: the approved client scan consent text.** D1 currently names that required text rather than supplying the words. The founder supplies it before live client consent checks; offline placeholder consent is test data, not approved legal copy.

**HIBP:** only applicable if domain search is free for the founder's domains and a shipped integration is enabled with the already-listed HIBP_API_KEY. No paid domain-search call or acceptance row is enabled by merely setting that key. HIBP is outside the shipped scan inventory verified here; this sheet neither adds a paid service nor tests the absence of a future route.

Offline proof uses fake external services, real shipped handlers/engines and disposable loopback stores. It does not claim founder live acceptance or production deployment. See `tests/radix_sheet/PR.md` for defects fixed at the top of this PR and the source inventory.
