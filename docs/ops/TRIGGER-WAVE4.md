## Decisions I made

1. Reuse C1, M1/M2 and B1, with no second CRM database, answering engine or publisher. Workspace reads and proposals use `commandRequest`; identity and tenant-admin status are derived server-side from the active Clerk organization. There is no organization creation on these page reads. Every side effect is a durable Command card and requires Confirm. Previews show the server-prepared payload and stale snapshots are refused. Cancel cancels the durable card.
2. The first Composer confirmation can create a W1 draft using the existing paid-guarded drafting corridor. It does **not** approve unseen generated copy. The resulting draft is opened for review; Approve then confirms that exact revision. Changed reply text likewise goes through a checked draft/edit confirmation before the existing reply-send confirmation. Existing runtime model routes and guards are unchanged; build/tests made no model calls.
3. Add only `trigger_bot_config.settings` and `trigger_bot_messages.person`, above the generated-memory boundary. They inherit their existing tables' conditional platform RLS, forced tenant boundaries and B1 retention. No new policy/table or destructive schema operation is introduced. `tank/main.py::_startup` was read before pushing the schema; its guard and schema ordering are unchanged.
4. Visitor requests retain B1's origin-bound public embed key and trusted-proxy/rate-limit handling. The embed runs in a shadow root in the store document, **not an iframe**, so the store's Origin survives authentication. The region comes from the existing embed key; ZA never falls back to US. Neither Workspace's key nor provider tokens reach the widget. Public replies expose only the existing answer/source/session fields; polling requires the exact tenant, conversation and visitor.
5. Unknown or unparseable opening hours, a missing/invalid zone, a disabled bot and absent evidence fail to hand-over rather than generating an availability claim. Opening hours use an explicit weekly local schedule, described below. Human replies are stored for the web widget only; this does not add a WhatsApp send path or bypass W3's free-reply gate.
6. Visitor forms create drafts. First/last names, quote title, requested quantity and request text are preserved. The existing Rig quote request carries that metadata without calculating a new price, amount, invoice or payment. Store confirmation is still required before C1/Rig activation. Form submission itself makes no model call. The single Contact slot on a quote accepts an explicit `Name <email>` contact; a name is never inferred from an email address. Lead capture accepts either an email or a phone number.
7. CRM reads retain explicit projections. Assignees and item/payment rows can be displayed; public invoice tokens/links, credentials and creator email metadata remain excluded. The C1 corridor does not support delete/send/convert/payment mutation actions today, so those framed controls remain disabled. The shared Clients/Opportunities/Cases/Tasks entries and Voice page are outside this wave's available page contracts and are disabled rather than linked to invented pages. Write continues to `/chats`.
8. TikTok/YouTube and unsupported account connections remain Off/disabled. Instagram, LinkedIn and X retain scheduled-only behavior; this wave adds no publishing/media support for them. Facebook execution requires the existing M2 implementation from #624; it is not copied or reimplemented here.
9. DST scheduling accepts only a unique local wall time in the explicit IANA zone. A nonexistent or repeated time is refused before a proposal; no offset is guessed. Bounded public transports, retries, uncertain delivery and reconciliation remain owned by B1/M1/M2.

## Configure and embed

Use the existing confirmed `trigger.bot.source.add`/FAQ/source tools to approve this store's sources. The existing source flow returns its origin-bound public key. No secret setting or new service is added. Configure the store's hand-over email through the existing B1 configuration; this page never returns that address to visitors.

Opening hours are explicit JSON, keyed Monday `0` through Sunday `6`, with local half-open time intervals. Closed days use `[]`. For example, placeholder test data might contain `{"0":[["08:00","17:00"]],"1":[["08:00","17:00"]]}`. The store supplies the actual schedule and IANA `time_zone`. Missing days are closed. Overnight opening is represented as separate intervals on the two days. Prose is retained as owner data but is not guessed into a schedule.

The `trigger.bot.settings` confirmed tool accepts the store's actual name, greeting, no-source and hand-over messages, IANA zone, hours, optional client colours and the founder-approved `privacy_notice`/`notice_version`. The Settings page edits its framed fields; notice and brand fields use the existing confirmed tool until their own UI frames are supplied. A first settings save uses the verified active business name, not a sample client name.
