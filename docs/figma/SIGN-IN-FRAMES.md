## Exactly what is configurable

- Instance defaults and organization overrides. The effective branding is selected by the authorization request's organization scope and project branding behavior.
- `lightTheme.logoUrl`, `darkTheme.logoUrl`: separately uploaded original logos; `lightTheme.iconUrl`, `darkTheme.iconUrl`: separately uploaded icons. Icons are browser/small-surface assets, not an extra decorative control inside the form.
- Each theme exposes only `backgroundColor`, `primaryColor`, `warnColor`, `fontColor`. Login derives its shade ramps, contrast and secondary text from those values; card and input surfaces are not independent brand settings.
- `fontUrl`: one uploaded custom UI font. Inter is proposed for the entire login; separate Jost headings cannot be configured through this single setting. Logos retain their own original artwork. Email font support depends on the mail client; the native template's fallback family remains applicable.
- `hideLoginNameSuffix`, `disableWatermark`, `themeMode` (`LIGHT`, `DARK`, `AUTO`/unspecified). Use hidden suffix/watermark. Sign-in is light only under the founder ruling of 3 Nov, 11:37 PT. Dark previews remain unused history. Existing language controls remain native chrome; use the native light-only setting where supported.
- Login V2 text overrides: `PUT /v2/settings/hosted_login_translation`, scoped with `instance: true` or `organizationId`, plus `locale: "en"` and `translations` containing actual locale namespaces/keys. The old Console login-text editor does not configure Login V2.
- Email messages: `SetCustomVerifyEmailMessageText`, `SetCustomPasswordResetMessageText`, `SetCustomInitMessageText`. Each accepts `title`, `preHeader`, `subject`, `greeting`, `text`, `buttonText`, `footerText`, scoped to a language and organization (instance equivalents also exist). Native message types: `VerifyEmail`, `PasswordReset`, `InitCode`. Preserve supported Go-template substitutions such as `{{.DisplayName}}`, `{{.Code}}`, `{{.PreferredLoginName}}`. The action URL is supplied by the identity provider, not invented in the design.
- Email subject/preheader/title are shown as Figma review metadata, not invented body elements. The native email body supplies logo, greeting, text, action and optional footer; its outer width, 180px logo, typography and spacing remain the native template. The native email renderer uses `policy.Light` only: email previews therefore use light branding, not a fictitious `darkTheme` email switch. Mail clients may independently restyle an email.

## Native constraints, not new settings

The default Login app uses its existing `top-to-bottom` / `flat` / `regular` layout, 440px outer wrapper, 16px wrapper gutters, 24px horizontal and 32px vertical card padding, 24px heading and 40px input. The native small action button is 36px tall; native email action height follows its own template. These are upstream defaults, not branding sliders. No custom CSS, two-column marketing panel, product navigation, new authentication method, new button or custom browser passkey dialog is proposed.

Native flow prerequisites (not changed here): local username/password authentication enabled; email login enabled and phone login disabled for the requested “email or username” label; registration and external providers not enabled in these views; password reset visible; an enrolled passkey/TOTP for those requested steps. These are existing login-policy choices, not merely branding. Data placeholders represent native runtime values and are not real accounts or secrets.

**Device denial limit:** current `denyDeviceAuthorization` returns to `/device` through the native consent component fallback. No dedicated denied-confirmation page or translation key exists. The requested post-denial frame therefore shows the actual code-entry screen, with a Figma-only annotation explaining the return. It does not invent a “Device denied” message inside the live UI. Approval uses the native `/signedin` page; its close-window notice is hardcoded upstream and must remain unchanged under this brief.

**Error limits:** backend error descriptions such as `Errors.User.Locked` and `Errors.User.Code.Expired` are upstream, read-only messages, not Hosted Login Translation overrides. Where shown, the exact existing wording is retained and mapped as read-only. It is not falsely presented as a new configurable key. Wrong-password copy uses the actual `password.errors.failedToAuthenticate` key with its runtime attempt placeholders. The native `Alert` component uses fixed yellow warning styling and neutral information styling; branding `warnColor` does not recolour that component. Native input/disabled-control styles are also retained. Empty input forms show their native disabled Continue control; enabled consent/passkey and email actions show the proposed primary colour.

**Passkey limit:** the operating-system/browser verification sheet is outside the identity provider branding and is not drawn. Only the existing Login app passkey page and controls are proposed.

All frame status ribbons, client-example labels, screen IDs, state captions and mapping notes are Figma-only review annotations. They are explicitly excluded from deployable message texts. Each text layer is named with its source key or `FIXED`/`FIGMA ONLY` provenance.
